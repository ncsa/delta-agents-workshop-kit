# Helper sheet: triage on Oct 5

The triage table from `design/ops.md`, updated with the Sep 28 dry runs and
red-team. Find the symptom, check the cause, apply the fix, and escalate only
when the fix does not work.

The participant's own steps are on `quick-card.md`; know it by heart. Most
fixes below start with two commands in a second Code Server terminal:

```bash
source /work/hdd/<code>/ws-kit/env.sh
ws-status          # module (from the checkpoints), node, jobs, reservation state
```

## Expected, not a fault

| What you see | Why | Say |
|---|---|---|

The facilitator calls the room's times; a late arrival works through the same steps |
| The agent works for several steps without asking | Milestone pacing (C18): after the plan is approved it works through each milestone and explains as it goes. ## Triage

| Failure | Likely cause | Fix | Escalate to |
|---|---|---|---|
| Duo or login fails | Enrollment or device binding, or the account is not fully provisioned | Walk through a Duo re-push; check `ws-roster` for that NetID's pre-flight | Floor captain, then Delta ops if many people hit it |
| Code Server session stays queued | Form values wrong: account not `<code>-delta-cpu`, partition not `cpu`, or duration over 1:45; or the reserved CPU nodes are full: the session then waits for a slot, or starts in the general queue | `squeue -u <netid> -o '%T %R %v'` (the reason; `%v` is the reservation, empty outside it); relaunch with the quick card values, Reservation empty. Still queued after 5 minutes: the login node is the outlet (ssh, `source /work/hdd/<code>/ws-kit/env.sh && ws-init`, `cd ~/ws-2026-10-05`, `hpc-gpt`) | Lead ops |
| Code Server or a job fails with "Requested reservation is invalid" | A reservation typed into the Code Server form (or an `srun --reservation` by hand) that does not exist. The workshop's reservation is magnetic: jobs on the workshop accounts go into it with no reservation named | Relaunch with the Reservation field empty; jobs go through `ws-submit`, which names none. `scontrol show reservation <reservation>` shows the real one (also on `ws-status`'s `reservation (magnetic)` line) | Lead ops |
| GPU job queued for many minutes | No free A40 on the reserved GPU nodes: the job waits for a slot there, or starts in the general queue | `squeue -j <id> -o '%T %R %v'` and `squeue --start -j <id>`. Leave the job queued; the agent gives the reason and checks again on the participant's next message (`go`). Level 3 in `ws-check` needs the participant's own job. | Lead ops if many jobs queue |
| The agent keeps calling `ws-wait` and asks nothing | The job is still PENDING or RUNNING; exit 4 from `ws-wait` is not an error | Tell the participant to press Esc and type "why is it still queued?" | — |
| The agent asks which account or partition to use | `WS_*` variables are empty in the agent's shell: `echo $WS_ACCOUNT_GPU $WS_PART_GPU $WS_RES_GPU` prints nothing | Quit the agent, `source /work/hdd/<code>/ws-kit/env.sh`, `cd ~/ws-2026-10-05`, `hpc-gpt`, type `start` | Lead ops |
| A red "Upstream error", or a reply that stops in the middle of a step; expect it most at M5, when everyone submits | Lumen errors bunch up when the whole room submits at once; a pause of about a minute is a rate-limit retry | Type `continue` once: the agent checks `PROGRESS.md` and the queue before it repeats anything. A pause: wait. Switch `/models` only after two failures in a row in the same session | Standby operator if many sessions fail at once |
| Model stops answering, or "stream error" | Lumen hiccup, rate limit (the NCSA key's pool is shared with every hpc-gpt user on Delta), or an HTTP 500 | Esc, resend once; then `/models` to the next model on the list (`qwen3.8-27b`, tested; then `qwen3.8-flash` and `qwen3-coder-next`, both untested as the workshop agent); Workshop standby only when `ws-standby status` shows it up (quick card §4). The agent resumes from `PROGRESS.md` | Standby operator |
| The first message fails with "model not available" or "No access to this model" | A workspace or session that names a model Lumen does not serve (`glm-5.3-flash` was removed on Oct 4; `glm-5.3` lost access for a few hours on Oct 5 and is back as the default) | `/models`, choose `glm-5.3` or `qwen3.8-27b`. To bring an older workspace up to date: `ws-init --refresh-kit`, then restart the agent. `ws-models` in the workspace shows which models answer | Lead if the default fails for many |
| "Error: No access to this model" | The key in use (`lumen key:` in `PROGRESS.md`) cannot use that model | `ws-models` in the workspace shows which models answer; switch with `/models`, or the participant uses a personal key (`~/.config/lumen/key`, mode 600, then `ws-init`) | Lead if it is the default model |
| "Model '<id>' not found" | Lumen removed the model: the kit's list is stale | Switch with `/models` to a model `ws-models` shows as ok | Lead: removes the id from `WS_LUMEN_MODELS` and republishes; participants rerun `ws-init --refresh-kit` |
| Which key is this participant on? | `lumen key:` in `PROGRESS.md`: `site` (the NCSA key hpc-gpt ships), `personal` (`~/.config/lumen/key`), `workshop` (the project key). `ws-init --lumen-key site\|personal\|workshop\|auto` changes it; a key file readable by others is refused (`chmod 600 ~/.config/lumen/key`) | `ws-models` after any change | — |
| Cold opencode start (over 60 s, or a timeout) | Not the cache: a cold `$HOME` starts in about 6 s. Look at the network or the provider: opencode retries silently every 120 s on provider errors | Run `ws-preflight` for that user (check 7 names the error); switch to Workshop standby with `/models` meanwhile | Standby operator |
| A submit is rejected for too many jobs | `ws-submit` allows two GPU jobs queued or running per participant (Q32) and names them; it is not a QOS limit | `squeue -u <netid>`; wait for one, or ask the agent to `ws-cancel --yes` a stale job of ours. Never `scancel -u`: it cancels the Code Server session too | — |
| `ws-submit` refuses "two GPU jobs already queued or running" | The Q32 cap: at most two GPU jobs per participant, pending or running | Wait for one, or `ws-cancel --yes <id>` | — |
| Compute node cannot reach Lumen or the standby | Egress blocked | Try `https_proxy=httpproxy.ncsa.illinois.edu:3128` (confirm with Delta ops first) | Delta ops |
| Agent wants to `pip install torch` (or similar) | It is installing its own multi-GB copy instead of using the module's (home quota, CUDA mismatch) | Deny the prompt; point it at AGENTS.md rule 17 and the topic's module | — |
| Agent runs heavy work in the Code Server session, or on a login node | It skipped `ws-submit` | Interrupt with Esc; tell it to use `ws-submit`. On `dt-login*`, relaunch through Code Server (the quick card values) | Lead ops if a login node is slow |
| Session dies after the agent opened an image | The model is text-only | Restart the agent (`hpc-gpt` in the workspace) and type `start`: it resumes from `PROGRESS.md`. The participant opens PNGs in the Code Server file browser | — |
| Harness crash | A real crash, or the stdin/TTY race known from Claude Code (`claude-code#12507`, unverified for opencode) | `hpc-gpt` in the workspace, then `start`: it resumes from `PROGRESS.md`. If it recurs, switch that participant between Code Server and `srun --pty` (a Code Server relaunch uses the quick card values) | Operator |
| M2 runs long (planning still going when the room moves on) | The participant is weighing every choice, or the agent surveys too much | Tell the participant to type "use the example plan"; the agent shows the topic's `PLAN.example.md` as the plan and adds the approval line once they approve it in words | — |
| `ws-submit --yes` says "approve the plan first: …" | The `PLAN.md` it names has no line starting with `approved:` (an indented one does not count), or the line has no value, or it still holds the template's `<...>` placeholder. The message says which | The participant reads PLAN.md and approves it in words ("I approve"; "ok" or "go on" is not an approval); the agent then writes `approved: <netid> <HH:MM>` at the start of a line and commits. Never add it for them | — |
| `ws-submit --yes` refuses "the open-ended budget is used up" | M7's budget (Q43): 10 open-ended jobs per workspace, any state (`WS_OPEN_JOBS_MAX`); about 50 people share 8 A40s and 2 CPU nodes | The agent writes up what it has in `open/RESULTS.md`; `ws-status` shows "open-ended jobs: N of 10". The prepared topic's jobs are not counted. Nobody can raise the budget: suggest a plot from the existing logs, `open/RESULTS.md`, or the take-home | Lead if a participant lost jobs to a fault |
| `ws-submit` rejects `--nodelist`, `--exclude` or `--nodefile` | Slurm and the reservation place workshop jobs; a pinned job stacks on one node, often a Code Server host (C21: an agent pinned 7 jobs to its own session node) | Remove the `#SBATCH` line and submit again | — |
| A reply ends with "Maximum steps for this agent have been reached" | The workshop agent's 30-step cap per reply (`ops/README.md`); its last step is left undone | Type `go on`; the agent continues. Then check its last step happened (`ws-status`, `PROGRESS.md`) | — |
| `/init` rewrote AGENTS.md (or CLAUDE.md, GEMINI.md) in the workspace | `/init` was run in `~/ws-2026-10-05`; it belongs in the participant's own project folders (`ON-YOUR-OWN.md`) | In the workspace: `git checkout -- AGENTS.md` (and `CLAUDE.md`, `GEMINI.md` if changed), then restart the agent and type `start` | — |
| The agent asks to edit `ON-YOUR-OWN.md`, `AGENTS.md` or a file under `guide/`, or one of them is damaged | These are kit files: the agent reads them and points to them, it never edits them | Answer Reject. In M7-M8 recommend Allow once, not Allow always, for file edits. A damaged `ON-YOUR-OWN.md`: `git checkout -- ON-YOUR-OWN.md` if it is not committed yet; else `cp /work/hdd/<code>/ws-kit/workspace-template/ON-YOUR-OWN.md ~/ws-2026-10-05/` (`ws-init --refresh-kit` keeps a file the participant changed) | — |
| The agent writes "taking that as a yes", or acts on "ok" or "go on" as an approval | Only an approval typed in words counts ("approved", "I approve"); "ok", "go on" and "keep going" do not | Press Esc, or Reject the prompt that follows; then type what you actually want | — |
| "The agent goes too fast" | Milestone pacing: several narrated steps per reply after the plan is approved | The participant types "slow down": one step per reply until "go ahead". They can also deny a prompt and ask why | — |
| M7: a `pip install` into `open/.venv` fails | No network from that node, a package that needs a compiler or a newer Python, or a name typo | Quote the error line to the agent. Try once more with the exact package name; otherwise use the module as it is. Never `pip install --user`, never inside a job, never `torch` from pip | Lead ops if every install fails (egress) |
| M7: the job says `ModuleNotFoundError` for a package the venv has | The venv is not active inside the job, or the job loads another module than the one the venv was made on | In `open/job.sbatch`: `module load <the same module>`, then `source .venv/bin/activate` (the template's `VENV=.venv`), before the program | — |
| M7: `open/AGENTS.md` confused the agent (it follows a rule there over the workspace AGENTS.md, or asks which one applies) | `open/AGENTS.md` holds only the mini-project's rules (module, venv, job script, evidence line); the workspace AGENTS.md still applies and wins on any conflict | Tell the agent: "the workspace AGENTS.md wins; make `open/AGENTS.md` say so". It edits the file (the harness asks), then carries on | — |
| M7: "Disk quota exceeded" in `$HOME` | The venv or `open/data` is too big for the home quota | `quota`; `du -sh ~/ws-2026-10-05/open/.venv ~/.cache/pip`. Delete the venv with approval (single files only for the agent; a helper removes the directory) and use the module as it is; keep data small | Lead ops |
| Participant lost or overwhelmed | The session is a full agenda for a newcomer | Pair up; suggest typing "run the prepared job unchanged" | Floor captain if widespread |
| BYO CLI auth fails | The participant's own Claude Code or Codex credentials | Best effort only; offer opencode (`hpc-gpt` in the workspace) instead; Claude Code and Codex cannot use Lumen | — |
